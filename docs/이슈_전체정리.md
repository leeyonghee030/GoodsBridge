## 작업 내용
공통 예외처리 체계를 만듭니다. 모든 도메인이 이 위에서 예외를 던지므로 가장 먼저 끝내야 합니다.

## 📋 범위
- `ErrorCode` enum (HttpStatus, 코드, 메시지) — 앞으로 모든 도메인이 계속 추가해서 씀
- 커스텀 Exception 5종 (생성자로 `ErrorCode`를 받음): `BadRequestException` / `UnauthorizedException` / `ForbiddenException` / `NotFoundException` / `InternalServerException`
- `GlobalExceptionHandler` (`@RestControllerAdvice`) — 위 5종 + `@Valid` 실패(`MethodArgumentNotValidException`) 처리
- 에러 응답 포맷 통일: `{ code, message, timestamp }`

## 🔍 유효성 검사 — 이 이슈가 전체 팀의 기준을 정합니다
- Request DTO에 Bean Validation 어노테이션(`@NotBlank`, `@NotNull`, `@Size`, `@Positive`, `@Email` 등)을 붙이면, 실패 시 Spring이 던지는 `MethodArgumentNotValidException`을 이 이슈의 `GlobalExceptionHandler`가 받아서 400 + 통일된 에러 포맷으로 응답해야 합니다.
- 각 도메인(B/C/D)은 **이 핸들러가 다 처리해주니 직접 try-catch 안 해도 됩니다** — 이걸 PR 설명에 예시로 남겨서 다들 알게 하기.

## 🔐 권한 체크 — 공통 기준 정의
- **401 Unauthorized**: 로그인 자체가 안 된 경우 (토큰 없음/만료) → `UnauthorizedException`
- **403 Forbidden**: 로그인은 됐지만 권한이 없는 경우 (예: 남의 가게 수정 시도) → `ForbiddenException`
- 이 둘의 구분을 PR 설명에 한 줄로 남겨서, 다른 도메인이 "내 가게 아닌데 수정하려고 하면 뭘 던져야 하나" 안 헷갈리게 하기

## 🧩 B/C/D는 이렇게 ErrorCode를 추가하세요 (초보자용)

`ErrorCode.java`는 **전원이 같이 쓰는 파일**입니다. 본인 도메인에서 필요한 에러가 생기면 아래 순서로 하면 됩니다.

**1단계 — 필요한 에러 상황 확인**
예: Shop 담당(B)이 "존재하지 않는 가게 id로 조회했을 때" 처리가 필요하다면 → 404(Not Found) 상황.

**2단계 — `ErrorCode.java`를 열어서 맨 아래에 한 줄 추가** (중간에 끼워넣지 말고 항상 **맨 아래**에 추가 — 이유는 아래 "충돌 방지" 참고)
```java
public enum ErrorCode {

    INVALID_REQUEST(HttpStatus.BAD_REQUEST, "요청 값이 올바르지 않습니다"),
    UNAUTHORIZED(HttpStatus.UNAUTHORIZED, "로그인이 필요합니다"),
    FORBIDDEN(HttpStatus.FORBIDDEN, "권한이 없습니다"),
    NOT_FOUND(HttpStatus.NOT_FOUND, "리소스를 찾을 수 없습니다"),
    INTERNAL_ERROR(HttpStatus.INTERNAL_SERVER_ERROR, "서버 내부 오류입니다"),

    // 👇 본인 도메인 코드는 이렇게 맨 아래에 추가
    SHOP_NOT_FOUND(HttpStatus.NOT_FOUND, "가게를 찾을 수 없습니다");
}
```

**3단계 — 본인 코드에서 사용**
```java
Shop shop = shopRepository.findById(id)
        .orElseThrow(() -> new NotFoundException(ErrorCode.SHOP_NOT_FOUND));
```
공통으로 쓸만한 상황이면 `ErrorCode.NOT_FOUND`처럼 이미 있는 걸 그냥 써도 됩니다. 메시지를 더 구체적으로 보여주고 싶을 때만 새 코드를 추가하세요.

**충돌 방지 — 왜 항상 "맨 아래"에 추가해야 하나?**
같은 파일을 B, C, D가 동시에 고치면 Git이 "충돌(conflict)"이라고 할 수 있는데, **다들 파일 맨 끝에만 한 줄씩 추가**하면 Git이 거의 항상 알아서 둘 다 합쳐줍니다. 반대로 중간에 끼워넣으면 충돌 날 확률이 높아집니다.

**그래도 충돌이 나면?**
파일 열어보면 이렇게 표시됩니다:
```
<<<<<<< HEAD
    SHOP_NOT_FOUND(...),
=======
    ITEM_NOT_FOUND(...),
>>>>>>> origin/develop
```
**둘 다 필요한 코드라 둘 다 지우지 말고, 화살표/등호 줄만 지우고 두 줄 다 남기면** 됩니다:
```java
    SHOP_NOT_FOUND(...),
    ITEM_NOT_FOUND(...),
```

## 이슈 #15 — [FEAT] 공통 SecurityConfig + JWT 발급/검증 유틸

**담당: A**

> ✅ **B/C/D가 바로 쓸 수 있는 자리만 먼저 만들어둠**: `_core.util.SecurityUtil.getCurrentUserId()` — 지금은 호출하면 항상 `UnauthorizedException`을 던지는 상태(아직 로그인 로직이 없으니 당연함). **이 이슈를 끝낼 때, JWT 인증 성공 시 `Authentication`의 principal에 `User.id`(Long 타입)를 세팅해야 `SecurityUtil`이 실제로 동작합니다.** B/C/D는 이미 이 메서드를 호출하는 코드를 미리 써둘 수 있음.

## 🎓 처음 해보는 사람을 위한 가이드 (세션 로그인만 배웠다면 먼저 읽기)

부트캠프에서 배운 건 보통 "Interceptor + 세션" 로그인이고, 이 이슈는 **OAuth2(카카오 로그인) + JWT**라서 개념이 꽤 다릅니다. 아래 순서로 읽으면서 만들면 됩니다.

### 1. 세션 로그인이랑 뭐가 다른가

| | 세션 로그인 (배운 거) | JWT (이 이슈) |
|---|---|---|
| 로그인 성공 후 | 서버가 세션ID 만들어서 **서버 메모리/DB에 저장** | 서버가 유저 정보를 담은 토큰을 **서명해서 발급만 하고 저장 안 함** |
| 클라이언트가 들고 다니는 것 | 세션ID (쿠키) | JWT 토큰 문자열 |
| 다음 요청 올 때 | 서버가 세션 저장소에서 **그 세션ID 찾아서** 누구인지 확인 | 서버가 토큰의 **서명만 검증** (저장소 조회 없음) |
| 특징 | Stateful (서버가 상태를 기억함) | Stateless (서버는 아무것도 기억 안 해도 됨) |

**왜 이렇게 바꾸는가**: 세션 방식은 로그인한 사람이 많아지면 서버가 그 상태를 다 들고 있어야 해서(여러 서버로 늘리면 세션 공유 문제도 생김 — 그래서 보통 Redis로 세션을 공유함). 이 프로젝트는 Redis를 안 쓰기로 했어서(CLAUDE.md 참고), 서버가 아무것도 저장 안 해도 되는 JWT 방식이 더 맞습니다.

**JWT 토큰 안에는 뭐가 들어있나**: 토큰은 사실 "유저 id 같은 정보(claim) + 발급시각/만료시각 + 서버만 아는 비밀키로 만든 서명" 이 세 부분을 이어붙인 문자열입니다. 서버는 이 서명을 다시 계산해서 비교만 하면 "이 토큰이 내가 발급한 게 맞고, 안 변조됐다"는 걸 알 수 있어요 — 그래서 DB 조회가 필요 없는 겁니다.

- Access 토큰: 실제 API 호출할 때 매번 들고 다니는 토큰. **수명이 짧음** (탈취돼도 피해 최소화)
- Refresh 토큰: Access 토큰 만료되면 "새 Access 토큰 다시 줘"라고 요청할 때 쓰는 토큰. **수명이 김**

### 2. OAuth2(카카오 로그인)는 또 뭔가

우리가 직접 "비밀번호 맞는지" 검증하는 게 아니라, **카카오한테 "이 사람 로그인 확인해줘"를 대신 맡기는 것**입니다. Spring Security가 이 과정 대부분을 이미 자동으로 처리해줘서, 우리가 직접 만들 코드는 생각보다 적습니다.

### 3. 전체 흐름 (이 순서대로 코드가 호출됩니다)

```
① 유저: "카카오로 로그인" 버튼 클릭
② 브라우저 → GET /oauth2/authorization/kakao (Spring Security가 기본 제공, 우리가 안 만듦)
③ 카카오 로그인 페이지로 리다이렉트 → 유저가 카카오 계정으로 로그인 + 정보제공 동의
④ 카카오 → GET /login/oauth2/code/kakao 로 콜백 (인가코드 들고 옴, 이것도 Spring Security가 처리)
⑤ Spring Security가 그 인가코드로 카카오한테 "이 사람 프로필 정보 줘" 요청 (자동)
⑥ 우리가 만드는 CustomOAuth2UserService 호출됨
   → 카카오가 준 프로필(id, nickname) 파싱
   → #5의 UserRepository.findOrCreateByKakao(...) 호출 (있으면 조회, 없으면 생성)
⑦ 로그인 성공 처리 → 우리가 만드는 AuthenticationSuccessHandler 호출됨
   → 여기서 우리 JWT(Access + Refresh) 발급
   → 프론트로 전달 (쿠키 or 쿼리파라미터)
⑧ 이후 모든 API 요청에 클라이언트가 Authorization: Bearer {accessToken} 헤더를 붙여서 보냄
⑨ 우리가 만드는 JWT 인증 필터가 매 요청마다
   → 헤더에서 토큰 꺼냄 → 서명/만료 검증
   → 통과하면 SecurityContext에 "이 요청은 User.id=N이 보낸 거다" 세팅
⑩ 컨트롤러/서비스에서 SecurityUtil.getCurrentUserId()로 그 id를 꺼내서 씀
```

②③④⑤는 Spring Security가 거의 다 해주고, **우리가 실제로 코드를 쓰는 지점은 ⑥⑦⑨** 세 군데입니다. 체크리스트의 `CustomOAuth2UserService` / `AuthenticationSuccessHandler` / `JWT 인증 필터`가 각각 이 지점입니다.

### 4. 만들 파일별로 "뭘 하는 애인지" 한 줄 요약

| 파일 | 역할 |
|---|---|
| `SecurityConfig` | "어디는 로그인 없이 들어올 수 있고, 어디는 막을지" + `oauth2Login()` 켜기 |
| `CustomOAuth2UserService` | 카카오가 준 정보를 우리 User로 변환 (⑥번 지점) |
| `AuthenticationSuccessHandler` | 로그인 성공 "다음에" 뭘 할지 — 여기서 JWT 만듦 (⑦번 지점) |
| JWT 유틸 (`JwtUtil` 등) | 토큰 생성 / 검증 / 안에서 유저 id 뽑아내기 |
| JWT 인증 필터 | 매 요청마다 토큰 검사해서 "누가 보낸 요청인지" 표시 (⑨번 지점) |

### 5. 막혔을 때 체크리스트 (흔한 실수)

- [ ] 카카오 개발자 콘솔의 **리다이렉트 URI**가 `application.yaml`/`.env`에 적은 거랑 **글자 하나까지 정확히 일치**하는지 (`http://localhost:8080/login/oauth2/code/kakao`)
- [ ] `permitAll` 범위에 `/oauth2/**`, `/login/**`을 안 넣으면 로그인 시도 자체가 401로 막힘
- [ ] JWT 서명 비밀키(`secret`)를 `.env`에서 가져오는지, 하드코딩 안 했는지
- [ ] Access 토큰 만료시간을 너무 짧게 잡으면 테스트하다가 계속 401 떠서 헷갈릴 수 있음 — 개발 중엔 넉넉하게 잡고 나중에 줄이기
- [ ] `/api/users/me` 호출했는데 403이 아니라 401이 뜨면 → 토큰 자체가 안 실려있거나 필터 등록이 안 된 것. 403이면 토큰은 통과했는데 권한 문제.

## 📋 범위
- `SecurityConfig`: 필터체인 + `oauth2Login()` 설정 (일단 API는 전체 `permitAll`, 범위는 아래 기준으로 좁힘)
- **카카오 OAuth2 로그인 연동**: `application.yaml`에 이미 등록된 `spring.security.oauth2.client.registration.kakao` 설정을 사용. `CustomOAuth2UserService`에서 카카오 프로필(id, nickname) 파싱 → `#5`의 `UserRepository.findOrCreateByKakao(...)` 호출
- **커스텀 `AuthenticationSuccessHandler`**: 카카오 로그인 성공 시 User 기준으로 Access/Refresh JWT 발급 → 프론트(Mustache 화면)로 전달 (쿠키 또는 redirect 쿼리 파라미터로 — 화면 작업(#24) 시 방식 확정)
- JWT 발급/파싱 유틸 (Access/Refresh)
- JWT 인증 필터 (API 요청 헤더에서 토큰 꺼내 `SecurityContext`에 세팅 — 로그인 이후의 일반 API 호출용)

## 🔐 permitAll 범위 — 다른 도메인 작업 전에 미리 합의할 것
- 로그인 없이 접근 가능해야 하는 것: `/oauth2/**`, `/login/**`(카카오 로그인 흐름 전체), 조회성 GET 다수 (`/api/shops`, `/api/items`, `/api/boards` 등 — 목록/상세 조회는 비로그인도 가능하게)
- **정적 리소스/화면(Mustache) 경로도 permitAll 필요**: `/css/**`, `/js/**`, `/test/**`(지금 떠 있는 placeholder 화면들), 그리고 화면이 실제로 교체되는 경로(`/login`, `/items` 등)도 추가. 화면 자체는 누구나 접근 가능해야 하고, 그 안에서 호출하는 API만 JWT로 막는 구조입니다.
- 로그인 필요: 그 외 POST/PATCH/DELETE 전부
- 이 경계가 바뀔 때마다 **PR 설명에 바뀐 내용 적고 팀 채팅에도 공유** (안 하면 남의 API가 갑자기 401)
